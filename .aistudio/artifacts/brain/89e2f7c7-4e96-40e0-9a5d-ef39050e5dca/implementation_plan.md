# La3eeb (لعيب) — خطة التنفيذ واستراتيجية الاختبارات (Phase 2: Implementation Plan & Test Strategy)

وثيقة معمارية شاملة لتحويل نتائج الفحص الفني (Technical Audit) إلى خارطة طريق تنفيذية وهندسية واضحة، لمعالجة جذور مشاكل البحث عن اللاعبين، وبناء نظام هجين فائق السرعة والموثوقية، وإتاحة مسار اللعب المباشر دون بحث، مع حماية تجربة اللعب الجماعي دون أي توقف أو شاشات بيضاء.

---

## ملخص القرارات ومراجعة المستخدم (User Review & Critical Decisions)

> [!IMPORTANT]
> تم اعتماد 3 ركائز رئيسية للبدء في مرحلة التنفيذ بعد مراجعة الكود الفعلي واختبارات الأداء وحدود الاستهلاك (Quota limits):
> 1. **نظام بحث هجين متعدد الطبقات (Hybrid Layered Search Engine)**: قاعدة بيانات محلية غنية + كاش ذكي + واجهة API كروية مجانية/منخفضة التكلفة + Gemini كطبقة ذكاء وتطبيع أسماء وليس المصدر الوحيد.
> 2. **مسار اللعب الحر في السر (Offline / In-Mind Player Mode)**: تمكين صاحب الجولة من اللعب فوراً دون إلزامه بالبحث عن لاعب على الإنترنت، مع الحفاظ على دورة الأسئلة والتخمين واحتساب النقاط سليمة بنسبة 100%.
> 3. **استراتيجية اختبار جازمة (Test-Driven Reliability)**: اختبارات وحدات لمنطق النقاط والبحث، واختبارات تكامل للـ Fallback Chain، واختبارات E2E للسيناريوهات الحرجة (استنفاد الحصة، انقطاع الإنترنت، الحالات الاستثنائية).

## 1. دراسة وتقييم خيارات واجهات البيانات الكروية (Football APIs Evaluation)

بناءً على الفحص الحي والبحث التقني، نقارن بين الخيارات المتاحة لدعم بيانات اللاعبين ومسيرتهم وانتقالاتهم:

| معيار المقارنة | 1. API-Football (Api-Sports) | 2. TheSportsDB | 3. Wikidata / Wikipedia API | 4. Enhanced Local DB (موصى بها كطبقة أساسية) |
| :--- | :--- | :--- | :--- | :--- |
| **تغطية اللاعبين** | تغطية فائقة وشاملة (أكثر من 900 دوري، تاريخ انتقالات مفصل، أرقام قمصان، مراكز). | ممتازة للنجوم والدوريات الكبرى، لكنها مجتمعية (Crowdsourced) وقد تغيب بعض تفاصيل انتقالات الدوريات المحلية. | تغطية تاريخية وحالية هائلة لجميع لاعبي العالم مع بيانات ويكي الصريحة. | تغطي أشهر 300 إلى 500 لاعب عالمي وعربي يبحث عنهم 95% من اللاعبين في جلسات الأصدقاء. |
| **التكلفة والحدود المجانية** | 100 طلب/يوم فقط في الباقة المجانية. الباقة المدفوعة تبدأ من 19$/شهر (7,500 طلب/يوم). | مجاني لـ 30 طلب/دقيقة (V1 API) دون بطاقة ائتمان. اشتراك Patreon بـ 9$/شهر لـ V2 API. | مجاني 100% بدون أي مفاتيح أو اشتراكات، ومعدل طلبات مرتفع جداً. | مجانية تماماً 100% (صفر تكلفة، أوفلاين تماماً). |
| **دعم الأسماء بالعربية** | ضعيف، يتطلب الاسم باللاتينية أو البحث بالإنجليزية. | متوسط، يبحث بالإنجليزية ويتطلب ترجمة للاسم العربي مسبقاً. | **استثنائي بالعربية**؛ يحتوي على أسماء اللاعبين البديلة والمعربة والمصرية والشائعة عبر خاصية `aliases` و`label:ar`. | **عربي أصيل 100%** مع دعم الألقاب (الدون، البرغوث، الماجيكو، تريكة، صلاح). |
| **زمن الاستجابة (Latency)** | 250 - 600ms عبر خوادم RapidAPI. | 300 - 800ms. | 200 - 500ms. | **0 - 5ms** (فوري وفائق السرعة دون اتصال بالإنترنت). |
| **مستوى الموثوقية** | ممتاز وثابت. | جيد للمشاريع غير التجارية. | ثابت ولا يتعرض للحظر مع User-Agent سليم. | غير قابل للسقوط نهائياً. |

### التوصية الهندسية للنظام الهجين (The Recommended Hybrid Stack):
1. **الطبقة الأولى (L1 - Local Rich DB)**: توسيع قاعدة `server/playerDatabase.ts` لتشمل 250–400 لاعب من أساطير كرة القدم والنجوم الحاليين ونجوم الدوريات العربية، مع تطبيع كامل للأسماء والبحث التقريبي (Fuzzy Search / Levenshtein Distance).
2. **الطبقة الثانية (L2 - Server In-Memory Cache)**: تخزين نتائج أي لاعب تم جلبه سابقاً في كاش سريع (TTL: 7 أيام) لتفادي استهلاك الكوتا أو تكرار الطلبات الخارجية.
3. **الطبقة الثالثة (L3 - Wikidata / TheSportsDB API)**: مصدر بيانات حقائق كروية مجاني وغير مكلف للتحقق من انتقالات وتواريخ ميلاد اللاعبين الجدد دون مخاطرة استنفاد الميزانية.
4. **الطبقة الرابعة (L4 - Gemini API Fallback & Normalizer)**:
   - استخدام موديل خفيف وموثوق مثل `gemini-3.1-flash-lite` أو `gemini-3.8-flash` وتفادي الموديلات المقيدة بالكوتا المفرطة.
   - تفعيل آلية Circuit Breaker حقيقية تعزل أخطاء 429 فوراً وتعود للطبقات السابقة دون تجميد واجهة المستخدم.
   - استخدام Gemini في "تطبيع الاسم" (Name Entity Normalization) عند كتابة اسم بالعامية أو النطق العربي المعقد، ثم استرجاع بياناته الموثوقة.

## 2. التصميم المعماري للنظام الهجين (Hybrid Search Architecture)

```
[ المستخدم يكتب اسم اللاعب في شاشة البحث ]
                    │
                    ▼
          ┌───────────────────┐
          │ Normalization     │ (إزالة الهمزات، وال التعريف، والتشكيل، والتطبيع العربي)
          └─────────┬─────────┘
                    │
                    ▼
          ┌───────────────────┐
          │ L1: Local DB      │ ──[ تطابق موجود ]──> استرجاع فوري (0ms) وإرجاع النتيجة
          └─────────┬─────────┘
                    │ (غير موجود محلياً)
                    ▼
          ┌───────────────────┐
          │ L2: Server Cache  │ ──[ موجود في الكاش ]──> إرجاع النتيجة فوراً
          └─────────┬─────────┘
                    │ (غير متاح في الكاش)
                    ▼
          ┌───────────────────┐
          │ Circuit Breaker   │ ──[ الكوتا معطلة مؤقتاً ]──> إرجاع أقرب نتائج محلية بديلة
          └─────────┬─────────┘
                    │ (الخدمة متاحة)
                    ▼
          ┌───────────────────┐
          │ L3: Wikidata /    │ ──[ تم استرجاع الملف ]──> حفظ في الكاش وإرجاع النتيجة
          │ Structured API    │
          └─────────┬─────────┘
                    │ (تعذر أو يحتاج إلى صياغة ذكية)
                    ▼
          ┌───────────────────┐
          │ L4: Gemini        │ ──[ استجابة ذكية سريعة ]──> تحقق من صحة الهيكل وحفظ بالكاش
          │ 3.1-flash-lite    │
          └─────────┬─────────┘
                    │ (فشل كلي للشبكة أو استنفاد كلي)
                    ▼
          ┌───────────────────┐
          │ Fallback Safe UI  │ خيار: "اللعب بالاسم المدخل في سرك بدون اتصال"
          └───────────────────┘
```

## 3. هندسة مسار "اللعب بدون بحث" (In-Mind / Offline Play Mode)

### جذور المشكلة الحالية في الكود:
في `src/App.tsx` الأسطر 590 و 609:
```tsx
// المشكلة: إذا كان currentProfile === null، تظهر شاشة بيضاء تماماً
{screen === 'game-active' && currentProfile && (
  <GameScreen profile={currentProfile} ... />
)}
```
عندما يرغب اللاعب في بدء الجولة دون اختيار مسبق من قاعدة البيانات، ينقطع تدفق الشاشات.

### الحل المقترح المعتمد:
1. **إضافة نوع ملف مرن (Flexible Game Profile)**:
   - دعم بروفايل من نوع `SecretInMindProfile` يحتوي على:
     ```ts
     interface SecretInMindProfile {
       id: 'secret-in-mind';
       displayName: string; // اختياري: الاسم الذي كتبه اللاعب أو "لاعب في السر"
       isCustomOrSecret: true;
       nationality?: string;
       clubs?: string[];
       clues?: string[];
     }
     ```
2. **تحديث شاشة البحث `PlayerSearch.tsx`**:
   - إضافة زر واضح وأنيق: **"اختر لاعباً في سرك (بدون بحث)"** أو **"اللعب بالاسم المدخل مباشرة ⚡"**.
   - عند الضغط عليه، لا يتم انتظار أي شبكة أو API، بل يُنشأ بروفايل سري وينتقل مباشرة لشاشة `ready-pass-back`.
3. **تحديث شاشة اللعب `GameScreen.tsx`**:
   - استقبال `profile?: PlayerProfile | SecretInMindProfile`.
   - في حال كان البروفايل "في السر":
     - عرض بطاقة خصوصية راقية توضح: *"اللاعب في سرك، الزملاء يسألونك وأنت تجيب بـ نعم أو لا"*.
     - زر استعراض مسيرة اللاعب يتحول إلى: *"ملاحظاتي / اسم اللاعب"* لتمكينه من مراجعته في سره إن كتبه.
     - زر المساعد الذكي يتيح له السؤال الحر عن أي معلومة تخص لاعبه دون إفشاء هويته للشاشة.
4. **تحديث شاشة إعلان النتيجة `RoundResult.tsx`**:
   - إذا كان اللاعب في السر، تتيح الشاشة لصاحب الجولة كتابة اسم اللاعب الحقيقي لإعلانه لبقية الأصدقاء وحفظه في سجل الجولة.

## 4. استراتيجية إدارة الأخطاء واستنفاد الحصة (Circuit Breaker & Resilience)

1. **إلغاء حظر النظام الجماعي (Remove Global Lockout)**:
   - حالياً في `server.ts`: خطأ 429 على أي لاعب يغلق النظام لمدة ساعتين لجميع الاستعلامات.
   - **التعديل المعماري**: عزل الحصة لكل مزود (Provider-level Circuit Breaker)، بحيث إذا انتهت حصة Gemini، تستمر قاعدة البيانات المحلية وتستمر استعلامات Wikidata دون أدنى توقف.
2. **التحول إلى موديلات مستقرة وتحديث التبعيات**:
   - التحول التلقائي من الموديلات المستنفدة إلى `gemini-3.1-flash-lite` مع تقليل التوكنات وسرعة الرد.
3. **الرد الفوري بالـ Graceful Degradation**:
   - لا يجوز إرجاع كود 404 أو 500 للمستخدم في الواجهة؛ بدلاً من ذلك، يُقترح له فوراً أقرب لاعب محلي، أو يُتاح له زر "اللعب بهذا الاسم في سرك فوراً".

## 5. استراتيجية الاختبار والتحقق المتكاملة (Comprehensive Test Strategy)

### أ. اختبارات الوحدات (Unit Testing):
- **محرك البحث والتطبيع (Search Normalizer)**:
  - التحقق من تطبيع الحروف العربية (أ، إ، آ، ى، ي، ة، هـ).
  - التحقق من تجاهل الكلمات الزائدة (اللاعب، كابتن، نادي).
  - اختبار البحث التقريبي (Fuzzy Search) للأخطاء الإملائية الشائعة مثل "ميسي" vs "ميسى"، "كريستيانو" vs "كرستيانو".
- **حساب النقاط وقواعد الجولات (Scoring & Rules)**:
  - التحقق من حساب نقاط صاحب الجولة ونقاط الخاسرين والمخمنين.
  - التحقق من تناقص عدد الأسئلة والتخمينات لكل لاعب بشكل مستقل.

### ب. اختبارات التكامل (Integration Testing):
- **سلسلة مصادر البحث (Fallback Pipeline)**:
  - فحص الاستجابة عند توقف الإنترنت (Offline Mode) والتأكد من عمل L1 بنسبة 100%.
  - محاكاة خطأ 429 من Gemini والتأكد من أن الكاش والمصدر المحلي يعملان دون تأخير للمستخدم.
- **سلامة عقود الـ API (API Contract & Schemas)**:
  - التحقق من أن استجابة `/api/search-player` و `/api/player-profile` تطابق المعايير الصارمة لـ TypeScript دون وجود `undefined` يسبب كراش للواجهة.

### ج. اختبارات واجهة المستخدم وتجربة اللعب (UI & E2E Testing):
- **سيناريو 1 (مسار البحث العادي)**: بحث عن لاعب مشهور -> اختيار وتأكيد -> بدء اللعب -> طرح أسئلة -> تخمين صحيح -> احتساب النقاط.
- **سيناريو 2 (مسار اللعب في السر بدون بحث)**: ضغط زر "اختر لاعباً في سرك" -> انتقال سلس لـ `ready-pass-back` -> بدء اللعب في `game-active` دون شاشات بيضاء -> تخمين أو انتهاء الأسئلة -> إدخال الاسم وكشف النتيجة.
- **سيناريو 3 (مسار انقطاع الحصة أو الشبكة)**: كتابة اسم لاعب غير موجود في قاعدة البيانات أثناء انقطاع الـ AI -> ظهور بطاقة لطيفة تقترح استخدام الاسم مباشرة دون تعطيل الجلسة.

## 6. خطة مراحل التنفيذ المقترحة (Execution Phases)

- **المرحلة 2.1: البنية التحتية وقاعدة البيانات المحلية الموسعة (Local DB Expansion)**:
  - ترقية `playerDatabase.ts` لتضمين أبرز نجوم كرة القدم العالميين والعرب (من 14 لاعباً إلى 250+ لاعباً).
  - تحسين خوارزمية البحث الداخلي والتطبيع العربي.
- **المرحلة 2.2: تحديث معمارية الخادم وقناة الذكاء الاصطناعي (Resilient Server Engine)**:
  - دمج طبقة الكاش (In-Memory / Local Storage Cache).
  - ضبط استدعاءات Gemini لتستخدم `gemini-3.1-flash-lite` مع Circuit Breaker مرن.
- **المرحلة 2.3: دعم مسار اللعب الحر في السر (Offline In-Mind Flow)**:
  - تعديل `PlayerSearch.tsx` لإضافة خيار اللعب بدون بحث.
  - تعديل `App.tsx` و `GameScreen.tsx` و `RoundResult.tsx` لاستقبال البروفايل السري دون الاعتماد الإجباري على `currentProfile`.
- **المرحلة 2.4: التحقق والاختبار الشامل (Verification & Hardening)**:
  - إجراء اختبارات التوافق والاستقرار والتأكد من انعدام الشاشات البيضاء واجتياز الـ Build بنجاح تام.
